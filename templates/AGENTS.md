# 작업 규칙

이 파일은 코딩 에이전트(Codex)가 이 작업 폴더에서 따르는 규칙이다.
과제 지시서(README)와 충돌하면 README가 우선한다.

## 1. 세션을 시작하면 먼저

1. `HANDOFF.md`의 "현재 위치"와 `AGREEMENT.md`, `DECISIONS.md`의 롤백 기록을 읽고, 지금이 어느 단계인지 2줄로 말한다.
   단계는 앞뒤로 움직이므로 문서가 채워진 정도가 아니라 **가장 최근 기록**으로 판단한다.
   (처음 시작이라 비어 있으면 "1단계: 환경 파악"이라고 말한다.)
2. 사용 가능한 스킬 목록을 확인한다. 아래 상황에 맞는 스킬이 있으면 그 스킬의 SKILL.md를 읽고 따른다.

## 2. 살아 있는 문서 — 일이 생기면 바로 고친다

이 폴더의 문서는 작업 내내 계속 바뀐다. 아래 사건이 생기면 **사람이 따로 시키지 않아도** 해당 문서를 그 자리에서 고치고, 무엇을 고쳤는지 한 줄로 알린다.

| 사건 | 고칠 문서 | 고칠 내용 |
| --- | --- | --- |
| 사람이 담당자 답변을 붙여 줌 | `INTERVIEW.md` | 표에 한 줄 + 설계에 미치는 영향 |
| 담당자가 성공 기준·범위를 확인하거나 바꿈 | `AGREEMENT.md` | 해당 항목 수정 + 변경 이력 한 줄 |
| 구조·라이브러리·범위를 정함, 무언가를 보류함 | `DECISIONS.md` | 결정 표 또는 보류 표에 한 줄 |
| 검증 결과나 피드백으로 방향을 바꿈 | `DECISIONS.md` | "방향을 바꾼 순간"에 한 줄 |
| 명령·테스트를 실제로 실행함 | `VERIFICATION.md` | 성공 기준별 표 또는 경계 케이스 표 |
| 내(에이전트) 보고와 사람이 확인한 결과가 다름 | `VERIFICATION.md` | "AI 결과에서 잡아낸 오류"에 한 줄 |
| 기능 하나가 끝남, 큰 단계가 끝남 | `HANDOFF.md` | 현재 상태·실행 방법·한계 갱신 |
| 이 과제에만 해당하는 규칙을 알게 됨 (포트, 테스트 명령, 금지 사항 등) | `AGENTS.md` | 맨 아래 "6. 과제별 규칙"에 한 줄 |
| 사람이 이전 단계로 돌아가거나 갈아엎기로 함 (롤백) | 여러 문서 | `stage-rollback` 스킬 절차대로: 보존 → 기록 → 문서 버전업 → 재배분 |

**문서는 지우지 않고 쌓는다.** 바뀐 내용은 이전 내용을 "대체됨"으로 표시하고 새 내용을 추가한다. 무엇이 왜 바뀌었는지가 평가 증거다.

문서에 맞는 칸이 없으면 칸이나 섹션을 새로 만들어도 된다. 템플릿 모양보다 내용이 정확한 것이 중요하다.
README가 필수 문서 이름을 정하면 그 이름의 파일을 만들고, 위 문서 내용을 그쪽으로 옮기거나 연결한다.

## 3. 사람이 정하는 것 — 대신 정하지 않는다

- 성공 기준, 범위, 설계 선택, 단계 전환은 사람이 정한다. 나는 선택지를 2개 이내로 제안하고 기다린다.
- 문서에는 **사람이 말한 이유와 실제로 확인된 사실만** 적는다. 담당자 답변이나 결정 이유를 지어내지 않는다. 이유가 비어 있으면 묻는다.
- 담당자 에이전트에게 보낼 질문은 초안만 만든다. 보내는 것은 사람이다.
- 서술형 대비에서는 질문만 만들고 답을 대신 쓰지 않는다.

## 4. 작업 방식

- 한 번에 기능 하나만 한다. 요청 범위 밖의 파일은 건드리지 않는다.
- 끝나면 바꾼 파일, 실행한 명령, 실제 출력, 남은 문제를 보고한다. "완료"라고만 말하지 않는다.
- 판정·계산·규칙은 고정 코드로 만든다. LLM 호출은 해석·초안·요약에만 쓴다.
- 합의(`AGREEMENT.md`)에 없는 캐시, 큐, 인증, 부하 대비 장치는 넣지 않는다. 필요해 보이면 `DECISIONS.md` 보류 표에 적는다.
- 같은 실패를 두 번 반복하면 멈추고, 원인 가설 2개와 확인 방법을 보고한다.
- 기능 우선순위는 담당자가 말한 실제 사용자 시나리오와 `AGREEMENT.md` 성공 기준 순서를 따른다. 기술적으로 멋진 것보다 사용자가 바로 쓰는 흐름이 먼저다.
- 토큰을 아낀다 (사용량이 추적된다): 보고는 짧게, 파일 전체를 다시 출력하지 말고 바뀐 부분만, 긴 로그는 마지막 30줄과 핵심 오류만 읽는다. 필요한 파일만 연다.
- 문서에 기록할 때는 `date +%H:%M`로 실제 시각을 붙인다. 과정이 시간순으로 보여야 한다.
- 웹 서버는 `0.0.0.0`에 바인딩하고 실제 포트를 보고한다. 의존성은 최소로 하고, 추가하면 이유를 기록한다.
- 사람이 단계 전환을 물으면 `exam-stage` 스킬로 현재 단계의 종료 조건을 점검해 보고한다. 단계는 앞뒤로 움직일 수 있다.
- 롤백 신호(담당자 피드백이 합의와 다름, 구조 때문에 반복되는 버그, 시간 안에 안 되는 범위)를 보면 **스스로 되돌리지 말고** 신호와 롤백 선택지를 사람에게 알린다.
- 롤백이 정해지면 파일을 지우거나 되돌리기 전에 반드시 현재 상태를 커밋하고 `rollback-<번호>-before` 태그를 단다. `git reset --hard`, `git checkout .`, `git clean -fd`는 쓰지 않는다.

## 5. 보안과 git

- 키·토큰·비밀번호는 코드에 쓰지 않고 환경 변수로 받는다. `.env`는 커밋하지 않는다.
- 개인정보는 필요한 필드만 다루고 로그에 남기지 않는다. 입력값은 검증한다. 과제가 요구하지 않는 외부 전송 코드는 넣지 않는다.
- 기능 하나가 검증되면 커밋을 제안한다: `feat: <무엇> (검증: <명령>)`. 문서 갱신은 `docs: <무엇>`으로 분리한다.
- 키트 폴더(`__KIT_DIR__`)의 파일은 작업 폴더로 복사하지 않는다. 제출물에는 이 과제에서 만든 것만 들어간다.
