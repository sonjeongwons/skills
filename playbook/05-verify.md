# 05. 검증·수용 (125~150분)

## 목표
성공 기준을 하나씩 직접 실행으로 확인하고, 담당자에게 결과를 보고해 수용을 확인받는다.

## 할 일
- [ ] 새 기능 중단. 버그 수정과 검증만 한다
- [ ] `VERIFICATION.md`: 성공 기준별 검증 방법·기대 결과·실제 결과·시각
- [ ] 화면 안 브라우저(0.0.0.0, 실제 포트)로 핵심 흐름을 사용자처럼 끝까지 조작
- [ ] 경계 케이스 3개: 빈 입력, 잘못된 형식, 매우 긴 입력
- [ ] 보안 점검 (`skills/security-review`): 키 하드코딩, 개인정보, 입력 검증
- [ ] Codex에게 "이 코드를 처음 보는 리뷰어로서 약점 3개" 요청 → 직접 확인 → 고칠지 한계로 남길지 결정
- [ ] 담당자에게 최종 보고: 성공 기준별 결과 + 남은 한계 → 피드백 기록
- [ ] 커밋

## 종료 조건
- 성공 기준마다 통과/미통과와 근거가 적혀 있다.
- 남은 한계가 목록으로 있다.

## 남길 증거 → 평가 기준
- 터미널의 테스트·실행 기록, `VERIFICATION.md` → 기술: 산출물을 직접 실행하고 검증
- "AI 결과에서 잡아낸 오류" 표 → 인지: AI에 끌려가지 않고 끌고 감
- 보안 체크 → 기술: 민감정보와 보안 위험 관리

## 하지 말 것
- Codex의 "테스트 통과했습니다"를 그대로 믿기. 같은 명령을 내가 다시 실행한다.
- 실패한 기준을 숨기기. 미통과는 한계로 적으면 인지 점수의 재료가 된다.

## 되돌아가는 신호 (125분 이후이므로 제한적)
- 핵심 기능 하나가 다른 기능을 깨뜨림 → 직전 정상 커밋으로 되돌림 (R4, `git revert`)
- 성공 기준이 측정 불가로 드러남 → 담당자에게 짧게 확인하고 `AGREEMENT.md`에 기록 (R1·R2를 5분 안에). 기준 자체를 바꾸지 말고 측정 방법을 바꾼다
- 구조 문제가 드러남 → 재설계하지 않는다. `HANDOFF.md` 한계와 "다음 할 일"에 쓰고 서술형에서 설명한다
