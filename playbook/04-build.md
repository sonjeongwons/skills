# 04. 설계·구현 (42~125분)

## 목표
70분까지 끝까지 도는 가장 작은 버전(v0)을 만들고, 이후 성공 기준 순서대로 확장한다.

## 할 일
- [ ] 설계 상담: 가장 단순한 구조 2안 비교 → 하나 선택 → `DECISIONS.md` D1 (`prompts/codex-prompts.md` §2)
- [ ] 작업 분해: 성공 기준 → 기능 목록 → 순서. 각 기능에 "완료 조건(실행 명령과 기대 결과)"을 붙인다
- [ ] 기능 하나씩 위임 (§3) → 오른쪽 셸에서 직접 실행 (§4) → 통과하면 커밋
- [ ] Codex가 일하는 동안: 다음 기능의 완료 조건 작성, 담당자 중간 보고, 이전 기능 검증
- [ ] v0 완성 시 담당자에게 화면/결과를 보여주고 피드백 받기 → `INTERVIEW.md` 하단
- [ ] 결정이 생길 때마다 `DECISIONS.md`에 한 줄
- [ ] 대화가 길어지면 `HANDOFF.md` 갱신 후 새 Codex 세션 (`skills/handoff`)

## 위임 단위
- 좋은 크기: 파일 1~3개, 완료 조건이 명령 하나로 확인되는 일
- 나쁜 크기: "구현 다 끝내 놔" — 10분 만에 결과가 나오지만 고치느라 토큰과 시간을 다 쓴다

## Codex 상태 읽기
- **승인 대기**: 기다리기만 하면 진행되지 않는다. 명령을 읽고 승인·거절한다.
- **실행 중**: 같은 요청을 반복하지 않는다. 그 시간에 다른 일을 한다.
- **완료**: 요청 완료 ≠ 과제 완료. 직접 검증한다.

## 종료 조건 (125분)
- 성공 기준 중 최소 핵심 1~2개가 직접 실행으로 확인됐다.
- 기능 단위 커밋이 여러 개 있다.

## 남길 증거 → 평가 기준
- 기능 단위 커밋과 diff → 기술: 유지·확장 가능한 구조 / 의도: 작업 분해
- 위임 프롬프트의 범위·완료 조건 → 의도: 작업을 나누고 AI에 위임
- 방향 전환 기록(`DECISIONS.md` 하단) → 의도: 진행에 따라 방향 조정
- `DECISIONS.md` → 인지: 구조를 선택한 이유

## 하지 말 것
- 합의에 없는 인프라(캐시, 큐, 인증, 부하 대비) 추가. 경력자일수록 빠지기 쉬운 함정이다. 필요해 보이면 "보류"에 적고 서술형에서 말한다.
- 읽지 않은 코드를 커밋하기. 핵심 파일은 직접 열어 데이터 흐름을 따라가 본다.
- 실패한 프롬프트를 그대로 재시도.
