# 09. 단계 롤백 — 되돌아가기와 갈아엎기

단계는 한 방향으로만 흐르지 않는다. 구현 중에 담당자 피드백이 합의와 다르면 인터뷰로 돌아가고, 검증에서 구조 문제가 드러나면 설계로 돌아가고, 문제를 잘못 이해했으면 처음부터 다시 한다.
**롤백 자체는 감점이 아니다.** 평가 기준 "진행에 따라 방향과 우선순위 조정"(의도 축)의 가장 강한 증거가 될 수 있다. 다만 **이유와 범위가 기록되지 않은 롤백**은 그냥 헤맨 것으로 보인다.

## 롤백 유형

| 유형 | 언제 | 돌아갈 단계 | 보존할 것 | 버릴 것 |
| --- | --- | --- | --- | --- |
| R1. 재인터뷰 | 담당자 피드백·새 정보가 합의와 다름, 성공 기준이 측정 불가로 드러남 | 2. 문제 발굴 → 3. 합의 | 동작하는 코드, 검증 기록 | 틀린 가정에 기댄 기능 계획 |
| R2. 재합의 | 범위가 시간 안에 안 됨, 성공 기준 우선순위가 바뀜 | 3. 서면 합의 | 코드 대부분 | 범위 밖이 된 기능 |
| R3. 재설계 | 구조가 성공 기준을 못 맞춤, 같은 버그가 구조 때문에 반복됨 | 4. 설계(구현 앞부분) | 합의, 인터뷰, 재사용 가능한 모듈 | 구조에 묶인 코드 |
| R4. 기능 되돌리기 | 마지막 기능이 다른 기능을 깨뜨림 | 4. 구현 (직전 커밋) | 그 전 커밋까지 | 문제 기능의 변경 |
| R5. 갈아엎기 | 문제를 잘못 이해했음, 접근 자체가 틀림 | 2 또는 3부터 | 인터뷰 기록, 배운 점 | 코드 거의 전부 |

## 시간에 따른 롤백 한계 (추정 기준)

| 경과 시간 | 허용 | 대신 할 것 |
| --- | --- | --- |
| ~70분 | R1~R5 모두 | — |
| 70~100분 | R1~R4. R5는 범위를 절반 이하로 줄일 때만 | 가장 작은 v0를 다시 정의 |
| 100~125분 | R1(짧게), R2, R4 | R3·R5 대신 현재 구조에서 범위 축소 + 한계로 기록 |
| 125분~ | R4만 | 나머지는 `HANDOFF.md` 한계와 "다음 할 일"에 적고 서술형에서 설명 |

## 절차 (어떤 유형이든 같은 순서)

1. **멈추고 신호를 말로 적는다** — 무엇을 보고 롤백을 생각했나 (담당자 발언, 실행 결과, 시간).
2. **현재 상태를 보존한다** — 버리기 전에 반드시.
   ```bash
   git add -A && git commit -m "wip: 롤백 전 상태 보존 (<이유 요약>)" --allow-empty
   git tag rollback-<번호>-before        # 예: rollback-1-before
   ```
   갈아엎기(R5)나 재설계(R3)면 이전 코드를 브랜치로도 남긴다: `git branch attempt-<번호>`
3. **유형과 목표 단계를 정한다** — 위 표에서 고르고, 남은 시간 한계와 대조한다. 결정은 사람이 한다.
4. **기록한다** — `DECISIONS.md`의 "롤백 기록" 표에 한 줄: 시각 / 유형 / 현재→목표 단계 / 신호 / 보존 / 버림 / 태그.
5. **문서를 고친다** — 지우지 않고 "대체됨"으로 표시한다. 이력이 증거다.
   - `AGREEMENT.md`: 버전을 올리고(v1→v2) 변경 이력에 이유
   - `INTERVIEW.md`: 새 회차로 질문을 이어 적음
   - `VERIFICATION.md`: 바뀐 코드에 걸린 검증 행에 "재검증 필요"
   - `HANDOFF.md`: 현재 단계와 롤백 이력 갱신
6. **코드를 되돌리거나 정리한다**
   - R4: `git revert <커밋>` (이력을 남기며 되돌림). `git reset --hard`는 쓰지 않는다.
   - 특정 파일만 이전으로: `git checkout <태그나 커밋> -- <경로>`
   - R3·R5: 새 구조를 만들고, 쓰지 않는 파일은 삭제 커밋으로 정리 (`git rm`)
7. **남은 시간을 다시 나눈다** — `00-timeline.md`의 넘지 말아야 할 선(70/125/170분)은 그대로 두고, 목표 단계부터 남은 단계에 시간을 다시 배분한다. 시간이 모자라면 범위를 먼저 줄인다.
8. **목표 단계의 플레이북 파일로 이동해 이어서 한다.**

## 하지 말 것

- 보존 없이 파일 삭제, `git reset --hard`, `git checkout .`
- 문서의 이전 내용을 지우고 새로 쓰기 (무엇이 바뀌었는지 사라진다)
- 이유 없이 같은 롤백을 두 번 반복하기 — 두 번째라면 범위를 줄인다
- 125분 이후 재설계·갈아엎기
- 롤백을 숨기기. 서술형에서 "왜 바꿨나"는 좋은 답의 재료다.
