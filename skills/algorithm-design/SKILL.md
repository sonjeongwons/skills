# 알고리즘 설계

목표는 "가장 똑똑한 알고리즘"이 아니라 **시간 안에, 맞다는 것을 보여줄 수 있는, 설명할 수 있는 알고리즘**이다.
서술형에서 "어떤 알고리즘을 썼고 왜인가", "입력부터 흐름을 설명하라"가 나온다. 이 절차의 기록이 그대로 답이 된다.

## 절차

1. **정식화** — 코드를 쓰기 전에 `DESIGN.md` 4.1을 채운다. 비어 있는 칸은 사람에게 묻는다(담당자에게 확인할 질문 초안도 만든다).
   - 결정 변수 / 목적 함수 / 제약(필수·선호 구분) / 입력 규모 / 시간 제한
   - 문제 유형을 이름 붙인다: 할당, 스케줄링, 배낭, 최단 경로, 매칭, 빈 패킹, 순위·점수화, 탐색, 예측
   - 목적이 여러 개면 가중합인지, 우선순위(사전식)인지 사람에게 확인한다.

2. **입력 규모로 방법 범위를 정한다** (대략의 기준)
   | 규모 | 가능한 방법 |
   | --- | --- |
   | 조합 수가 작음 (n ≤ 10~20) | 완전 탐색, 백트래킹 — 최적해 보장 |
   | 중간 | DP, 정수계획(설치된 솔버가 있을 때), 그래프 알고리즘(다익스트라, 매칭, 최대 유량) |
   | 큼, 시간 제한 짧음 | 탐욕 + 지역 탐색(2-opt, swap), 시뮬레이티드 어닐링 — 보장 없음, 기준선 대비 개선으로 보여준다 |
   | 판정·점수화 | 규칙 기반 점수 함수(가중치는 상수·설정 파일), 재현 가능해야 함 |
   설치된 라이브러리를 먼저 확인한다(`python -c "import scipy, ortools, pulp, networkx"` 등). 없으면 새로 설치하기 전에 사람에게 묻는다.

3. **기준 해법 먼저** — 가장 단순한 해법(완전 탐색이나 단순 탐욕)을 먼저 만든다. 이것이 정답 대조와 개선 폭 측정의 기준이 된다.

4. **방법 제안** — 2개 이내로 비교해 제안한다: 핵심 아이디어, 복잡도, 최적성(보장/근사/휴리스틱), 구현 위험, 70분 v0 가능성. **결정은 사람이 한다.** 결정되면 `decision-log`로 기록하고 `DESIGN.md` 4.2·4.3을 채운다.

5. **구현 규칙**
   - 목적 함수와 제약 검사를 **별도 함수**로 만든다: `score(solution)`, `is_feasible(solution)`
   - 알고리즘은 입력→출력 순수 함수로, 입출력(파일·API)과 분리한다
   - 난수를 쓰면 시드를 고정한다. 반복 횟수·시간 제한은 상수로 둔다
   - 해가 없으면 무엇을 반환하는지 정한다(빈 결과 + 이유)

6. **검증** — `DESIGN.md` 4.4와 `VERIFICATION.md`에 실제 결과를 적는다.
   - 작은 입력 여러 개에서 기준 해법(완전 탐색)과 결과·목적값 비교
   - 모든 출력에 `is_feasible` 통과
   - 실제 규모 입력에서 실행 시간
   - 기준선 대비 목적값 개선 폭 (숫자로)
   - 경계 입력: 빈 입력, 해가 없는 입력, 동점

7. **설명 준비** — `DESIGN.md` 2절(데이터 흐름)과 4절이 실제 코드와 일치하는지 확인하고, "대표 입력 1건의 여정"을 실제 값으로 채운다.

## 보고 형식

```
문제 유형: … / 목적: … / 제약: …
방법: … (복잡도 …, 최적성 …)
검증: 작은 입력 _건 정답 일치 / 제약 위반 0 / 기준선 대비 _% 개선 / 실제 규모 _초
한계: …
```

## 하지 말 것
- 정식화 없이 바로 구현
- 기준 해법 없이 "최적화했다"고 주장하기 (비교 대상이 없으면 개선을 보여줄 수 없다)
- LLM 호출로 최적화·판정하기 (재현 불가, 검증 불가)
- 시간 제한을 넘는 정확해 고집 — 근사해와 개선 폭으로 충분하다
- 설명할 수 없는 라이브러리 블랙박스 — 쓰면 무엇을 정식화해서 넘겼는지 설명할 수 있어야 한다
