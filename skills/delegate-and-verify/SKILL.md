# 위임과 검증 루프

## 입력 (사람이 준다)
- 기능 이름
- 범위: 수정해도 되는 파일
- 완료 조건: 실행할 명령과 기대 결과

입력에 완료 조건이 없으면 구현하지 말고 완료 조건부터 제안한다.

## 절차

1. **계획 3줄** — 바꿀 파일, 접근 방법, 위험한 지점을 먼저 말한다.
2. **구현** — 범위 안의 파일만 수정한다. 합의(`AGREEMENT.md`)에 없는 장치는 넣지 않는다.
3. **실행** — 완료 조건의 명령을 실제로 실행한다. 웹 서버는 `0.0.0.0`에 바인딩한다.
4. **보고** — 아래 형식으로만 보고한다.

```
바꾼 파일: …
실행한 명령: …
실제 출력(요약): …
완료 조건 충족: 예 / 아니오
남은 문제: …
```

5. **실패 시** — 같은 시도를 반복하지 않는다. 원인 가설 2개와 각각의 확인 방법을 보고하고 멈춘다.
6. **기록** — 실행 결과를 `VERIFICATION.md`에 한 줄 남긴다. 사람이 다시 실행해 결과가 달랐다고 알려 주면 "AI 결과에서 잡아낸 오류" 표에도 적는다. 설계 선택이 있었으면 `decision-log` 스킬로 넘긴다.

## 사람이 하는 일 (에이전트가 대신하지 않는다)
- 같은 명령을 오른쪽 셸에서 직접 다시 실행한다.
- 결과가 다르면 "내가 실행하니 X가 나왔다"로 수정 요청한다.
- 통과하면 커밋한다: `feat: <기능> (검증: <명령>)`
- 결정이 있었으면 `decision-log` 절차로 기록한다.

## 하지 말 것
- "완료했습니다"만 보고
- 범위 밖 리팩터링
- 테스트를 통과시키려고 테스트를 고치기 (테스트 수정이 필요하면 이유를 먼저 보고)
