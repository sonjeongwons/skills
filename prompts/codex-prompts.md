# Codex 프롬프트 모음

`[ ]`는 상황에 맞게 바꾼다. 지시서 전체를 붙여 넣지 않는다. 파일 이름으로 가리킨다.

## §1. 첫 프롬프트 — 지시서 구조화 (환경 파악 직후)

Cofa Probe 담당자가 시연에서 쓴 첫 질문에 맞춘 형태다.

```
README.md(과제 지시서)를 읽고 내가 해야 하는 요건과, 업무 담당자에게 확인해야 하는 부분을
불릿으로 구분해서 정리해줘. 지시서에 없는 내용은 추측하지 말고 '확인 필요'로 표시해.
필수 제출 문서와 파일명도 따로 뽑아줘. 아직 코드는 만들지 마.
```

## §1-b. 기존 자산 파악 (인터뷰하는 동안 맡겨 두기)

```
작업 폴더의 기존 코드·데이터·테스트를 훑고 구조를 10줄 이내로 요약해줘.
실행 방법이 있으면 명령만 알려주고 실행은 하지 마. 파일은 수정하지 마.
```

## §2. 설계 상담 (합의 직후, 구현 전)

```
AGREEMENT.md의 성공 기준을 만족하는 가장 단순한 구조를 2가지 제안해줘.
각각 만들 파일, 데이터 흐름, 실패할 수 있는 지점, 70분 안에 v0가 가능한지를 비교하고,
합의에 없는 요소(캐시·큐·인증·부하 대비 등)는 빼. 결정은 내가 할게.
```

결정 후:

```
[A안]으로 간다. 이유는 [이유]. 버린 대안은 [B안]이고 [이유]로 버렸다.
DECISIONS.md에 D1로 한 줄 추가해줘.
```

## §3. 위임 — 기능 하나

```
[기능]만 구현해. 범위: [파일들]. 다른 파일은 건드리지 마.
완료 조건: [명령]을 실행해서 [기대 결과]가 나오는 것.
끝나면 바꾼 파일, 실행한 명령, 실제 출력, 남은 문제를 보고해.
```

## §4. 검증 후 수정 — 내가 직접 실행한 결과로

```
내가 [명령]을 실행하니 [실제 결과]가 나왔어. 기대는 [기대 결과]였어.
원인 가설을 2개 말하고, 가장 가능성 높은 것부터 확인해서 그 부분만 고쳐.
고친 뒤 같은 명령을 다시 실행해서 결과를 보여줘.
```

## §5. 방향 전환

```
[검증 결과/담당자 피드백] 때문에 [무엇]을 [어떻게] 바꾼다.
영향받는 파일을 먼저 목록으로 보여주고, 내가 승인하면 진행해.
DECISIONS.md의 '방향을 바꾼 순간'에 한 줄 추가해줘.
```

## §6. 리뷰어 관점 약점 찾기 (검증 단계)

```
이 코드를 처음 보는 리뷰어라고 생각하고 약점 3개를 파일·함수 단위로 지목해줘.
각각 어떤 입력에서 실패하는지, 영향이 무엇인지 적어. 고치지는 마.
```

## §7. 보안 점검

```
작업 폴더 전체에서 하드코딩된 키·토큰·비밀번호, 로그에 남는 개인정보,
검증 없이 쓰이는 입력값, 과제에 필요 없는 외부 전송을 찾아 목록으로 보여줘. 고치지는 마.
```

## §8. 문서 정리

```
AGREEMENT.md, DECISIONS.md, VERIFICATION.md, git log를 바탕으로 [필수 문서명]을 작성해줘.
선택한 판단과 근거, 검증 결과, 남은 한계를 반드시 포함하고,
실제 코드·커밋에 없는 내용은 쓰지 마.
```

## §9. 서술형 리허설 (제출 전)

```
이 결과물에 대해 심사자가 물을 만한 질문 6개를 내줘. 답은 주지 마.
(구조 선택 이유, 동작 방식, 실패 조건, 확장, AI 결과 검증, 다음 개선 유형을 섞어서)
```

내 답을 쓴 뒤:

```
내 답이야: [답]. 실제 코드와 다른 부분만 파일·줄 근거로 지적해줘. 모범답안은 쓰지 마.
```

## §10. 세션 교체 (대화가 길어졌을 때)

```

```

새 세션에서:

```
HANDOFF.md, AGREEMENT.md, DECISIONS.md를 읽고 현재 상태를 3줄로 요약해.
그다음 '다음 사람이 할 일' 1번만 진행해.
```

(`~/kit`은 키트를 clone한 위치. 다른 곳에 받았다면 그 경로로 바꾼다)
