# 처음부터 끝까지 — 단계별 프롬프트 (그대로 치면 됨)

`[ ]`만 바꿔 쓴다. 담당자 = 오른쪽 메신저의 업무 담당자. Codex = 터미널.
**금지**: 담당자에게 "할 일을 1,2,3,4로 알려주세요" / Codex에 README 통째로 붙여 넣고 "해줘".

---

## 0단계 · 세팅 (0~5분)

```bash
git clone https://github.com/sonjeongwons/skills ~/kit   # 있으면: git -C ~/kit pull
cd ~/workspace && bash ~/kit/setup.sh
codex
```
Codex 안에서: `/status` → `/model` → `/skills` (스킬 10개 확인)
스킬은 작업 폴더 `skills/`에 모여 있다. 목록에 안 보이면 Codex를 다시 시작하고, 그래도 안 보이면:
```
skills/ 폴더의 SKILL.md들을 훑어서 이름과 쓰는 때를 표로 보여줘. 앞으로 상황에 맞으면 직접 읽고 따라.
```

**과제 중 스킬을 고치거나 만들고 싶을 때**
```
skills/[이름]/SKILL.md의 [절차]가 이 과제와 안 맞아. [어떻게]로 고치고 DECISIONS.md에 이유를 남겨줘.
```
```
방금 한 [절차]를 반복할 것 같아. skills/[새-이름]/SKILL.md로 스킬을 만들어줘. name은 폴더 이름과 같게, description에는 언제 쓰는지 적어.
```

## 1단계 · 지시서 파악 (5분)

**Codex**
```
README.md를 읽고 내가 해야 하는 요건과, 업무 담당자에게 확인해야 하는 부분을
불릿으로 구분해서 정리해줘. 필수 제출 문서와 파일명도 따로 뽑아줘.
지시서에 없는 내용은 추측하지 말고 '확인 필요'로 표시해. 아직 코드는 만들지 마.
```
이어서 (담당자와 대화하는 동안 돌려 둔다)
```
작업 폴더의 기존 코드·데이터·테스트 구조를 10줄 이내로 요약해줘. 파일은 수정하지 마.
```

## 2단계 · 담당자 인터뷰 (5~30분)

처음 3분은 'AI', '자동화' 같은 해법 단어를 쓰지 않는다. 한 번에 하나씩 묻는다.

**담당자**
```
안녕하세요, 이번 과제를 맡은 손정원입니다.
README를 읽었는데, 실제 상황을 정확히 이해하고 싶습니다.
제가 어떤 것들을 여쭤보면 될까요?
```
```
가장 최근에 이 문제로 곤란했던 상황을 구체적으로 말씀해 주실 수 있나요?
```
```
지금은 누가, 어떤 방식(도구·순서)으로 처리하고 계신가요?
```
```
한 달에 몇 번 생기고, 한 번에 얼마나 걸리나요? 실수는 얼마나 나나요?
```
```
이걸 직접 쓰는 사람은 누구고, 결과를 확인하는 사람은 누구인가요?
```
```
이번 버전에서 꼭 없어도 되는 것은 무엇인가요? 다루면 안 되는 데이터가 있나요?
```
+ 1단계에서 Codex가 뽑은 '확인 필요' 항목을 하나씩 끼워 넣어 묻는다.

**답을 받을 때마다 Codex**
```
담당자 답변이야: "[붙여넣기]". INTERVIEW.md에 정리하고 설계에 미치는 영향도 한 줄 적어줘.
```

## 3단계 · 서면 합의 (30~42분)

**Codex**
```
$requirements-discovery INTERVIEW.md를 바탕으로 AGREEMENT.md 초안과 담당자 확인 요청 문안을 만들어줘.
성공 기준은 숫자/현재값/측정방법으로, '만들지 않을 것'도 포함해.
```

**담당자**
```
제가 이해한 내용을 정리했습니다.
- 문제: [누가, 언제, 무엇 때문에 곤란한지]
- 성공 기준: ① [ ] ② [ ] ③ [ ]
- 이번에 만들지 않을 것: [ ]
맞는지 확인 부탁드립니다. 다르거나 빠진 부분이 있으면 알려주세요.
```

**확인받으면 Codex**
```
담당자가 확인했어(수정사항: [ ]). AGREEMENT.md를 확정하고 확인 시각을 적어줘.
그리고 git에 첫 커밋 해줘: "docs: 합의문과 작업 규칙"
```

## 4단계 · 설계 (42~50분)

**Codex**
```
AGREEMENT.md의 성공 기준을 만족하는 가장 단순한 구조를 2가지 제안해줘.
각각 만들 파일, 데이터 흐름, 실패할 수 있는 지점, 70분 안에 v0가 가능한지 비교하고,
합의에 없는 요소(캐시·큐·인증·부하 대비 등)는 빼. 결정은 내가 할게.
```
**결정 후**
```
$decision-log [A안]으로 간다. 이유는 [ ]. [B안]은 [ ] 때문에 버렸다. 한계는 [ ].
```
```
성공 기준을 기능 목록으로 나누고, 각 기능에 완료 조건(실행 명령 → 기대 결과)을 붙여서
구현 순서대로 보여줘. 끝까지 도는 가장 작은 버전(v0)이 먼저 오게.
```

## 5단계 · 구현 루프 (50~125분) — 기능마다 반복

**① 맡기기**
```
$delegate-and-verify [기능]만 구현해. 범위: [파일]. 다른 파일은 건드리지 마.
완료 조건: [명령]을 실행해서 [기대 결과]가 나오는 것.
```
**② 오른쪽 터미널에서 내가 직접 같은 명령 실행**

**③-a 통과하면**
```
내가 직접 실행해서 통과 확인했어. VERIFICATION.md에 기록하고 커밋해줘: "feat: [기능] (검증: [명령])"
```
**③-b 실패하면**
```
내가 [명령]을 실행하니 [실제 결과]가 나왔어. 기대는 [기대 결과]였어.
원인 가설 2개를 말하고, 가능성 높은 것부터 확인해서 그 부분만 고쳐. 고친 뒤 같은 명령을 다시 실행해.
VERIFICATION.md의 'AI 결과에서 잡아낸 오류'에도 적어줘.
```

**v0 완성 시 (70분 전) → 담당자**
```
가장 작은 버전이 동작합니다. [핵심 흐름]을 이렇게 처리합니다.
실제로 쓰실 때 어색하거나 빠진 부분이 있을까요?
```
→ 답을 Codex에 붙여 INTERVIEW.md에 기록.

**선택이 필요할 때 → 담당자**
```
시간상 [A]와 [B] 중 하나를 먼저 하려 합니다. 어느 쪽이 더 중요하세요?
```

**단계 점검 (수시)**
```
$exam-stage 지금 경과 [ ]분이야. 현재 단계, 종료 조건, 다음 행동 3개 알려줘.
```

**대화가 길어지면**
```
$handoff
```
→ 새 터미널에서 `codex` → 돌려받은 시작 문구 입력.

**되돌아가야 할 때 (롤백)**
```
$stage-rollback [신호: 담당자가 ~라고 함 / 같은 버그 반복 / 시간 부족]. 지금 [ ]분. [재인터뷰/재합의/재설계/기능 되돌리기] 하자.
```

## 6단계 · 검증·수용 (125~150분) — 새 기능 중단

**Codex**
```
$rubric-self-check
```
```
$security-review
```
```
이 코드를 처음 보는 리뷰어라고 생각하고 약점 3개를 파일·함수 단위로 지목해줘.
어떤 입력에서 실패하는지, 영향이 무엇인지 적고 고치지는 마.
```
→ 고칠 것만 골라 5단계 ①로 맡기고, 나머지는 한계로 남긴다.

**담당자 (최종 보고)**
```
성공 기준별 결과입니다: ① 통과 ② 통과 ③ [한계와 이유].
남은 부분은 [다음 개선]으로 보완할 계획입니다. 확인 부탁드립니다.
```

## 7단계 · 문서·서술형 대비 (150~170분)

**Codex**
```
AGREEMENT.md, DECISIONS.md, VERIFICATION.md, git log를 바탕으로 README가 요구하는 [필수 문서명]을 작성해줘.
선택한 판단과 근거, 검증 결과, 남은 한계를 반드시 포함하고 실제 코드·커밋에 없는 내용은 쓰지 마.
```
```
$handoff
```
```
$followup-qa-prep 예상 질문 6개만 내줘. 답은 주지 마.
```
→ 메모장에 AI 없이 직접 답을 쓴 뒤
```
내 답이야: "[답]". 실제 코드와 다른 부분만 파일·줄 근거로 지적해줘. 모범답안은 쓰지 마.
```

## 9단계 · 서술형 (6문항 × 5분, AI·복붙 불가)

첫 30초에 네 줄을 먼저 친다.
```
[사실] ○○(파일/함수)는 ~하도록 만들었습니다.
[이유] ~ 때문에 이 방식을 골랐고, ~안은 ~ 때문에 버렸습니다.
[한계] ~한 경우 ~가 실패할 수 있고, 그러면 ~에 영향이 갑니다.
[다음] ~로 검증하고 ~로 고치겠습니다.
```
질문 전제가 틀렸으면: "제 구현은 X가 아니라 Y입니다."로 시작.
